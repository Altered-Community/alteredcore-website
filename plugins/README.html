Overview

The plugin system lets developers add front-end pages, admin sections, CSS/JS assets and database tables to an AlteredCore site without touching any core file. Plugins live entirely in plugins/{your-plugin-id}/ and are loaded on demand.

The lifecycle of a plugin is:

  1. Developer creates the plugin folder and a plugin.json manifest.
  2. Developer packages the folder as a .zip file.
  3. An admin uploads the ZIP via Admin → Plugins → Install plugin.
  4. An admin clicks Activate. If the plugin has a SQL file, it runs automatically on first activation.
  5. The plugin's front-end pages are accessible at /pages/{slug}. Its admin sections appear in the sidebar for groups that have been granted the corresponding permission.
Plugins are PHP code. Installing a plugin is equivalent to granting its author server-side code execution rights. Only install plugins from sources you trust.

Plugin structure

plugins/
  my-plugin/
    plugin.json             # manifest — required
    pages/
      front.php             # one file per front-end page
      about.php
    admin/
      index.php             # one file per admin section
      settings.php
      inc/
        functions.php       # optional — admin-only helpers
    assets/
      style.css             # CSS and JS served as static files
      app.js
    api/
      data.php              # one file per HTTP API endpoint
    inc/
      functions.php          # optional — shared helpers for pages, admin, api
    sql/
      install.sql            # full schema — runs on first activation
      update_1.1.0.sql       # delta only — runs when upgrading to 1.1.0
      update_1.2.0.sql       # delta only — runs when upgrading to 1.2.0

There are no mandatory subdirectory names — the paths are declared in the manifest and can be anything. The only required file is plugin.json at the root of the plugin directory.

Manifest — plugin.json

The manifest is a JSON file at the root of the plugin directory. It declares the plugin's identity, pages, admin sections, assets and database tables.

{
    "$schema":      "../plugin.schema.json",
    "id":           "my-plugin",
    "name":         "My Plugin",
    "version":      "1.0.0",
    "description":  "A short description shown in the Plugins admin page.",
    "author":       "Your Name",
    "icon":         "fa-solid fa-star",
    "table_prefix": "mp",

    "pages": [
        {
            "slug":     "my-plugin",
            "file":     "pages/front.php",
            "title_en": "My Plugin Page",
            "title_fr": "Ma page plugin"
        }
    ],

    "admin": [
        {
            "section":  "my-plugin",
            "file":     "admin/index.php",
            "label_en": "My Plugin",
            "label_fr": "Mon Plugin",
            "icon":     "fa-solid fa-star"
        }
    ],

    "api": [
        {
            "endpoint": "data",
            "file":     "api/data.php"
        }
    ],

    "assets": {
        "css":        ["assets/style.css"],
        "js":         ["assets/app.js"],
        "global_css": ["assets/global.css"],
        "global_js":  ["assets/global.js"]
    },

    "sql":    "sql/install.sql",
    "tables": ["items"]
}

Fields reference

FieldDescription
$schemaoptionalPath to plugin.schema.json — enables IDE autocompletion and validation. Set to "../plugin.schema.json" when the plugin is inside the plugins/ directory.
idrequiredUnique slug. Lowercase letters, digits and hyphens only. Must match the directory name after extraction.
namerequiredHuman-readable name shown in the Plugins admin page.
versionrequiredSemver string, e.g. 1.2.0. Required — the installer uses this to determine whether an upload is an upgrade.
descriptionrequiredOne-line description shown in the Plugins admin page.
authorrequiredAuthor name or contact.
iconoptionalFont Awesome class used in the Plugins list, e.g. fa-solid fa-star.
table_prefixoptionalShort unique string used to namespace your database tables, e.g. "hw". Results in table names like altcore_plugin_hw_messages. Required if your plugin declares tables or uses qp().
pagesoptionalArray of front-end page declarations. See Front-end pages.
adminoptionalArray of admin section declarations. See Admin pages.
apioptionalArray of HTTP API endpoint declarations. See HTTP API endpoints.
assetsoptionalCSS and JS files to inject on the plugin's front-end pages, and/or on every page of the site. See CSS & JS assets.
sqloptionalPath to a SQL file (relative to plugin root) that runs once on first activation.
tablesoptionalArray of table name placeholders (without prefix). Shown in the delete confirmation — admin can choose to drop them when uninstalling.
A JSON Schema file (plugins/plugin.schema.json) is included in the repository. Adding "$schema": "../plugin.schema.json" as the first field of your plugin.json enables real-time validation and autocompletion in VS Code, PhpStorm and any other editor that supports JSON Schema draft-07.

Front-end pages

Each entry in the pages array registers one front-end page. The page becomes accessible at /pages/{slug} — exactly like a core page.

KeyDescription
slugrequiredURL segment: /pages/my-slug. Must be unique across core pages and all active plugins.
filerequiredPath to the PHP file, relative to the plugin root.
title_en / title_froptionalUsed by the router to set the default $pageTitle (HTML <title> + visible header) when the plugin page is loaded. The plugin page can override it by assigning $pageTitle anywhere before the HTML.

A front-end page file contains only business logic and HTML. The following variables are available without any setup:

  • $db — database connection, ready to use.
  • $isLoggedIn — whether the visitor is authenticated.
  • $pageTitle — set from the manifest's title_en / title_fr. Override by assigning a new value before the HTML.
  • getUiLang() — returns 'en' or 'fr', language is already initialized.
  • Site header and footer are rendered automatically.
<?php
// loginRequired(); // uncomment to restrict to logged-in users only

$txt = [
    'en' => ['page_title' => 'My Page'],
    'fr' => ['page_title' => 'Ma page'],
][getUiLang()] ?? [];

// Override the default title from the manifest (optional)
$pageTitle = $txt['page_title'];

$rows = $db->query(qp("SELECT * FROM {items} ORDER BY id DESC"))->fetchAll();
// $isLoggedIn is available for auth-conditional content
?>
<div class="container py-4">

    <div class="d-flex align-items-center justify-content-between mb-4">
        <div class="section-title mb-0"><span><?= h($pageTitle) ?></span></div>
    </div>

    <!-- Your content here -->

</div>
Auth guards work normally inside plugin pages. redirect() sends a Location header and exits — PHP headers are not affected by the router's output buffering, so the redirect fires correctly before the site chrome is rendered.

Showing and hiding plugin pages

Plugin pages can be individually hidden without deactivating the whole plugin. Go to Admin → Pages and find the plugin's pages in the Plugin pages table. Each row has a Show / Hide button (eye icon) that toggles the page's visibility instantly. A hidden page returns a 404 to visitors; the plugin's admin sections and database tables are unaffected.

This is useful when a plugin has several pages and only some should be publicly accessible at a given time.

Linking to pages

Linking to a plugin front-end page

Plugin pages are accessible at /pages/{slug}, exactly like core pages. Use BASE_URL to build absolute links so they work regardless of where the site is installed:

<!-- In a PHP template -->
<a href="<?= BASE_URL ?>/pages/my-slug">Go to my page</a>

<!-- Or as a PHP string -->
$url = BASE_URL . '/pages/my-slug';

You can also use a relative path if you are already on the same origin — but BASE_URL is safer when the site lives in a subdirectory:

<a href="/pages/my-slug">Go to my page</a>

Linking to a plugin admin page

The admin dispatcher URL follows the pattern /admin/plugin-page?plugin={id}&section={section}:

<!-- Sidebar link (generated automatically, but useful for redirects) -->
$adminUrl = BASE_URL . '/admin/plugin-page?plugin=my-plugin&section=my-plugin';

redirect($adminUrl);                   // after a POST action
header('Location: ' . $adminUrl);     // raw redirect

Linking from admin back to the front-end page

<a href="<?= BASE_URL ?>/pages/my-slug" target="_blank" class="btn btn-sm btn-outline-secondary">
    <i class="fa-solid fa-arrow-up-right-from-square me-1"></i> View page
</a>

Registering the page in the navigation menu

Plugin pages are not added to the site nav automatically. To add a nav item, either:

  • Go to Admin → Settings → Navigation and add the entry manually after activation, or
  • Insert the nav item from your plugin's SQL install file:
-- sql/install.sql
INSERT IGNORE INTO {nav_items}
    (`label_en`, `label_fr`, `url`, `icon`, `sort_order`, `is_visible`)
VALUES
    ('My Page', 'Ma page', '/pages/my-slug', 'fa-solid fa-star', 100, 1);
Use INSERT IGNORE so re-running the SQL (e.g. after a reinstall) does not create duplicate entries.

CSS & JS assets

The assets object supports two scopes:

KeyScopeDescription
cssPage-scopedInjected only on the plugin's own front-end pages.
jsPage-scopedInjected only on the plugin's own front-end pages.
global_cssGlobalInjected on every page of the site while the plugin is active.
global_jsGlobalInjected on every page of the site while the plugin is active.
global_phpGlobal (PHP)PHP files executed in <head> on every page. May output <script>, <link> or <style> tags. Use to inject PHP-computed data (e.g. configuration) as JS variables.

All four arrays can be combined freely. Files are served directly by Apache from the plugins/{id}/assets/ directory.

"assets": {
    "css":        ["assets/style.css"],
    "js":         ["assets/app.js"],
    "global_css": ["assets/global.css"],
    "global_js":  ["assets/global.js"]
}
  • CSS (css and global_css) is injected as <link> tags in <head>, after Bootstrap and the theme stylesheet.
  • JS (js and global_js) is injected as <script> tags just before the Bootstrap bundle in the footer.
  • Bootstrap 5 and Font Awesome are already loaded by the theme — no need to include them.
  • Multiple files are supported: add them in order to the array.

Global assets — typical use cases

Use global_css / global_js when your plugin needs to inject UI or behaviour that must be present on pages it does not own — for example:

  • A floating action button (FAB) fixed to a corner on mobile.
  • A persistent notification badge or toast container.
  • A site-wide keyboard shortcut handler.
  • A cookie banner or consent widget.

global_php — injecting PHP data into JS

global_php files are PHP scripts executed in <head> on every page. They can output any valid head content — the typical use case is exposing plugin configuration as a JS variable so that a global_js file can read it:

<?php
// assets/global_head.php
$config = require __DIR__ . '/../config.php';
$pages  = array_values((array)($config['pages'] ?? []));
?><script>window.MY_PLUGIN_CONFIG=<?= json_encode(['pages' => $pages]) ?>;</script>

The corresponding global_js file can then read window.MY_PLUGIN_CONFIG, which is guaranteed to be defined before the script executes (head PHP runs before footer JS).

Global assets (global_css, global_js, global_php) are loaded on every page while the plugin is active. Keep them small and fast. Wrap all JS in an IIFE; scope CSS selectors tightly with a unique ID or plugin-prefixed class; keep PHP files side-effect-free (output only, no redirects or session writes).

CSS layering — what goes where

Four layers apply to every page, loaded in this order. Each layer sits on top of the previous one:

#LayerFile(s)Rule
1 Bootstrap 5 CDN Use Bootstrap utilities and components in HTML before writing any CSS. Covers layout (container, row, col-*), spacing (mb-3, gap-2, p-4), text (text-muted, fw-bold, small), flex (d-flex, align-items-center), buttons (btn, btn-outline-secondary), modals, dropdowns, badges, forms, and more.
2 Site CSS css/style.css Shared site components that all pages and plugins can use. Never add plugin-specific styles here. Reuse these classes in your plugin templates — they are theme-aware and respond to dark mode automatically.
3 Plugin CSS plugins/{id}/assets/style.css Only write plugin CSS for elements that cannot be expressed with layers 1–2. Keep it to layout geometry and plugin-specific selectors. Use CSS variables from the site palette — never hard-code colours.
4 Active theme themes/{name}/style.css Loaded last. Overrides everything above. Plugins do not need to know which theme is active — themes reskin Bootstrap components (.dropdown-menu, .modal-content, .form-control…) and redefine CSS variables globally. Your plugin inherits all of this automatically.

Layer 1 — Bootstrap first

Always start with Bootstrap. Common utilities to reach for before writing any CSS:

  • Layout: container, row g-3, col-12 col-md-6, d-flex, align-items-center, justify-content-between, gap-2, flex-wrap, ms-auto
  • Spacing: mb-3, py-4, px-3, p-0
  • Typography: fw-bold, text-muted, small, fs-6, text-truncate
  • Components: btn btn-sm btn-outline-secondary, badge, alert alert-danger, input-group input-group-sm, form-control form-control-sm, form-select, modal fade + modal-dialog modal-dialog-centered, dropdown-menu + dropdown-item
  • Visibility: d-none d-md-block, position-relative, overflow-hidden, w-100, h-100

Layer 2 — Site CSS classes

After Bootstrap, reach for site-level shared classes before writing custom CSS. These are defined in css/style.css and automatically adapt to both themes and dark mode:

  • Cards / surfaces: card-altered — the site's standard card surface
  • Buttons: btn-primary-altered — the branded primary button
  • Page header: section-title — the underlined page title style
  • Tabs: ac-tabs + ac-tab (active state: active) — site-styled tab bar
  • State panes: ac-state-pane — empty/loading state panel
  • Notices: ac-notice ac-notice--warning, ac-notice--info — themed notice boxes
  • Modal surfaces: Bootstrap's modal-content, modal-header, modal-body, modal-footer are already themed by css/style.css (sand background, site border colours) and overridden per theme — use them as-is, without adding custom background or border colours.

Layer 3 — Plugin CSS (last resort)

Write plugin CSS only for things that genuinely cannot be achieved with layers 1–2. Typical legitimate uses:

  • Custom geometry: a specific max-height, a grid with a fixed column count, a sticky panel offset.
  • Transition or animation unique to the plugin.
  • A component that exists nowhere else in the site (e.g. a card-flip, a scanner overlay).

Always use CSS variables with fallbacks so themes can override:

/* Good — uses site variables, falls back gracefully */
.my-badge { background: var(--overlay-badge-bg, rgba(0,0,0,.7)); color: #fff; }

/* Bad — hard-coded colour, invisible to themes and dark mode */
.my-badge { background: #333; color: #fff; }
Never add plugin CSS to css/style.css. That file is global — it loads on every page. Plugin styles belong exclusively in the plugin's own assets/style.css.

Layer 4 — Themes override everything

The active theme's style.css is loaded after everything else. It redefines CSS variables (colours, glass effects) and overrides Bootstrap components. Your plugin does not need to handle themes at all — if you use Bootstrap classes and site CSS variables correctly, both themes (and dark mode) work automatically without any plugin changes.

If a theme needs to adjust something specific to your plugin, it can add a rule targeting your plugin's selector. No coordination needed between the plugin and the theme.

Practical checklist

  1. Need a button? → btn btn-sm btn-primary-altered or btn btn-outline-secondary. No custom CSS needed.
  2. Need a modal? → modal fade + modal-dialog modal-dialog-centered. Use style="--bs-modal-width:400px" for custom widths (not max-width). No custom background or border CSS needed — the site and theme handle it.
  3. Need a dropdown? → dropdown-menu + dropdown-item. Themed automatically including dark mode.
  4. Need a surface/card? → card-altered p-3. No custom CSS needed.
  5. Need a colour? → Use var(--primary-400), var(--neutral-600), var(--sand-200), etc. Never hard-code.
  6. Still need custom CSS? → Write it in assets/style.css using CSS variables. One targeted selector, no !important.

CSS variables — making your plugin theme-aware

The site exposes a CSS custom property palette in css/style.css :root. Use these variables in your plugin stylesheet instead of hard-coded colours so that your plugin automatically adapts when a theme changes the palette:

/* Instead of hard-coded colour: */
.my-badge { background: rgba(0,0,0,.7); color: #fff; }

/* Use a variable with a fallback — theme can override just the variable: */
.my-badge { background: var(--overlay-badge-bg, rgba(0,0,0,.7)); color: #fff; }

Palette groups available in all themes:

VariablesRole
--sand-50 … --sand-300Page and surface backgrounds
--neutral-100 … --neutral-800Text and border shades (100 = lightest, 800 = body text)
--primary-300 … --primary-500Brand accent (links, active buttons)
--modal-panel-bgModal / panel background (glass in altered-db theme)
--panel-borderModal / panel border color
--card-lightbox-bgFull-screen lightbox overlay background
--overlay-badge-bgSmall overlay badge on card images
--overlay-bar-bgBar overlay on card images

A theme can restyle your plugin with zero changes to your code — it only needs to redefine the relevant variables in its :root block.

PHP files inside plugins/ are blocked from direct HTTP access by the .htaccess at the root of the plugins directory. CSS, JS, images and fonts are served normally.

Admin pages

Each entry in the admin array registers one section in the admin panel. The section link appears in the sidebar for any user whose group has been granted the section permission.

KeyDescription
sectionrequiredUnique section slug used for permission checks. Must not conflict with core section names.
filerequiredPath to the admin PHP file, relative to the plugin root.
label_en / label_froptionalSidebar label in English and French.
iconoptionalFont Awesome class for the sidebar icon.

The admin page is accessed at /admin/plugin-page?plugin={id}&section={section}. The dispatcher validates the user's permission automatically before including the file. The page file does not need to call require_once header.php or getDB() — both are already handled:

<?php
// This file is included inside the admin layout.
// $db is pre-injected by the dispatcher — use it directly.
// All site functions and CSRF helpers are available.
// Do NOT include the admin header or footer again.

if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    if (!csrfValid($_POST['csrf_token'] ?? '')) {
        flash('Invalid token.', 'error');
        redirect(BASE_URL . '/admin/plugin-page?plugin=my-plugin&section=my-plugin');
    }
    // Handle your POST action...
}
?>

<div class="admin-header-bar">
    <h1><i class="fa-solid fa-star me-2"></i>My Plugin</h1>
</div>

<div class="card-altered p-3">
    <!-- Your admin UI here -->
</div>

Granting access to groups

Go to Admin → Groups, edit a group, and enable the section named after the plugin's section value. Members of that group will see the link in the sidebar.

TinyMCE rich-text editor

Admin pages can embed a full rich-text editor using TinyMCE. The site already has a TinyMCE API key configured via the TINYMCE_API_KEY constant. Always check that the constant is defined and non-empty before loading TinyMCE — if the key is absent the textareas fall back to plain <textarea> elements.

Loading TinyMCE

Load the script from the TinyCloud CDN, then call tinymce.init(). Both steps must be wrapped in the TINYMCE_API_KEY guard:

<?php if (defined('TINYMCE_API_KEY') && TINYMCE_API_KEY !== ''): ?>
<script
    src="https://cdn.tiny.cloud/1/<?= h(TINYMCE_API_KEY) ?>/tinymce/6/tinymce.min.js"
    referrerpolicy="origin">
</script>
<script>
tinymce.init({
    selector:      '#my_body',
    language:      '<?= getUiLang() === 'fr' ? 'fr_FR' : 'en' ?>',
    height:        400,
    menubar:       false,
    branding:      false,
    plugins:       'lists link image table code',
    toolbar:       'undo redo | blocks | bold italic underline | forecolor backcolor | alignleft aligncenter alignright | bullist numlist | link image | table | code',
    content_style: 'body { font-family: Arial, Helvetica, sans-serif; font-size: 15px; line-height: 1.7; }',
    // Keep the hidden textarea in sync so form submit POSTs current content.
    setup: function (editor) {
        editor.on('change', function () { editor.save(); });
    },
});
</script>
<?php else: ?>
<div class="alert alert-warning small">
    TinyMCE is not configured (<code>TINYMCE_API_KEY</code> is empty). Plain textarea active.
</div>
<?php endif; ?>
editor.on('change', () => editor.save()) is required. Without it, the form's hidden <textarea> is not updated when the user types, so the POST body is empty. TinyMCE replaces the textarea with an iframe and only writes back when you call save().

Multiple textareas

Pass a comma-separated CSS selector to selector to initialise several editors at once:

tinymce.init({
    selector: '#body_en, #body_fr',
    // ... rest of options
});

Textareas inside tabs / hidden panels

TinyMCE initialises correctly even when its parent element has display:none (the editor uses an absolute-height iframe). However, when the panel becomes visible after a tab switch, call a resize event so TinyMCE repaints its toolbar:

// In your tab-switching JS:
document.querySelectorAll('[data-tab]').forEach(function (btn) {
    btn.addEventListener('click', function () {
        // ... show/hide panels ...
        if (typeof tinymce !== 'undefined') {
            window.dispatchEvent(new Event('resize'));
        }
    });
});

Image uploads

PHP upload limits — If your plugin accepts file uploads, two PHP settings must both be large enough or $_FILES will be silently empty with no error:
  • upload_max_filesize — maximum size of a single uploaded file.
  • post_max_size — must be greater than upload_max_filesize.
Detection: $_FILES['f']['error'] === UPLOAD_ERR_INI_SIZE
Set in .htaccess: php_value upload_max_filesize 20M / php_value post_max_size 25M

The site provides a generic image upload endpoint at /admin/plugin-file-upload.php. It accepts a multipart POST, validates the file (image MIME types only, max 5 MB), and stores it in uploads/p_{plugin-id}/ — a public, PHP-execution-blocked directory. The subdirectory is created automatically on the first upload.

To enable image uploading in your TinyMCE editor, add the automatic_uploads flag and a custom images_upload_handler to your tinymce.init() call. The handler sends three POST fields: the file, your plugin id, and the admin section slug (used for permission checking — the upload is rejected if the current admin session does not have access to that section).

tinymce.init({
    selector:          '#my_body',
    plugins:           'lists link image table code',
    toolbar:           '... | image | ...',
    automatic_uploads: true,

    images_upload_handler: function (blobInfo, progress) {
        return new Promise(function (resolve, reject) {
            var fd = new FormData();
            fd.append('file',    blobInfo.blob(), blobInfo.filename());
            fd.append('plugin',  'my-plugin');      // your plugin id
            fd.append('section', 'my-section');     // your admin section slug

            var xhr = new XMLHttpRequest();
            xhr.open('POST', '<?= h(BASE_URL) ?>/admin/plugin-file-upload.php');
            xhr.withCredentials = true;
            xhr.upload.onprogress = function (e) {
                if (e.lengthComputable) { progress(e.loaded / e.total * 100); }
            };
            xhr.onload = function () {
                if (xhr.status < 200 || xhr.status >= 300) {
                    reject({ message: 'Upload failed (' + xhr.status + ')', remove: true });
                    return;
                }
                try {
                    var json = JSON.parse(xhr.responseText);
                    if (json.error) { reject({ message: json.error, remove: true }); return; }
                    resolve(json.location); // absolute URL inserted into the editor
                } catch (e) {
                    reject({ message: 'Unexpected server response', remove: true });
                }
            };
            xhr.onerror = function () { reject({ message: 'Upload error', remove: true }); };
            xhr.send(fd);
        });
    },

    setup: function (editor) {
        editor.on('change', function () { editor.save(); });
    },
});

The endpoint returns {"location": "https://…/uploads/p_my-plugin/20260510_123456_ab12cd34.jpg"}. TinyMCE uses this URL as the src attribute of the inserted <img> tag. Because the URL is absolute and the directory is publicly served, images remain accessible even when the content is displayed outside the admin panel — including inside newsletter emails sent to recipients.

Replace 'my-plugin' and 'my-section' with your actual plugin id and admin section slug. If the section value does not match a section the current admin has access to, all upload requests will return HTTP 403.
You do not need to declare the uploads/p_my-plugin/ directory anywhere — the upload endpoint creates it automatically. Files in that directory are served as static assets; PHP execution is blocked by uploads/.htaccess.

                }
                try {
                    var r = JSON.parse(xhr.responseText);
                    if (r.error) { reject({ message: r.error, remove: true }); return; }
                    resolve(r.location);
                } catch (e) { reject({ message: 'Bad response', remove: true }); }
            };
            xhr.onerror = function () { reject({ message: 'Upload error', remove: true }); };
            xhr.send(fd);
        });
    },
    setup: function (editor) {
        editor.on('change', function () { editor.save(); });
    },
});
</script>
<?php else: ?>
<div class="alert alert-warning mt-3 small">
    TinyMCE is not configured (<code>TINYMCE_API_KEY</code> is empty). Plain textarea active.
</div>
<?php endif; ?>

Database

If the plugin needs its own tables, declare the install file in the manifest:

"sql": "sql/install.sql"

install.sql runs automatically the first time the plugin is activated. It must contain the complete schema for that version — all tables, all default rows. It never re-runs after that.

Use {curly-brace} table placeholders — the same syntax as in PHP. The site automatically passes SQL files through qp() before executing them.

qp() automatically combines the site prefix, a plugin_ segment, your table_prefix, and the table name. You just write {tablename} — the namespacing is handled for you:

table_prefixYou writeResult (site prefix: altcore_)
"hw"{messages}`altcore_plugin_hw_messages`
"mp"{items}`altcore_plugin_mp_items`
Always use qp() for your plugin's tables — it automatically applies your plugin's prefix so you just write {tablename}. 
-- sql/install.sql  (complete schema for v1.0.0)
CREATE TABLE IF NOT EXISTS {items} (
    `id`         INT AUTO_INCREMENT PRIMARY KEY,
    `title`      VARCHAR(255) NOT NULL,
    `created_at` DATETIME     DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

INSERT IGNORE INTO {items} (`id`, `title`) VALUES (1, 'Default item');

Migration files

When you add tables or columns in a new version, create a migration file named update_{version}.sql containing only the delta — the changes since the previous version. The full schema goes in install.sql so fresh installs get everything at once.

When do migrations run? Migration files run automatically when you upload a new ZIP via Admin → Plugins. You do not need to deactivate/reactivate the plugin. The plugin stays in its current state (active or inactive) — the files are replaced and all applicable update_*.sql files are executed in version order before you see the result.

New table (v1.1.0):

-- sql/update_1.1.0.sql  (delta only — new table added in v1.1.0)
CREATE TABLE IF NOT EXISTS {settings} (
    `key`   VARCHAR(100) NOT NULL PRIMARY KEY,
    `value` TEXT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

INSERT IGNORE INTO {settings} (`key`, `value`) VALUES ('greeting', 'Hello!');

New column (v1.2.0):

-- sql/update_1.2.0.sql  (delta only — new column added in v1.2.0)
ALTER TABLE {messages}
    ADD COLUMN IF NOT EXISTS `author` VARCHAR(100) NOT NULL DEFAULT '' AFTER `text`;
Always update install.sql at the same time — add the new table or column there too, so users who install the new version directly get the full schema without needing the migration.
ScenarioWhat runs
Fresh install v1.0.0, then activateinstall.sql
Update from v1.0.0 → v1.1.0 (ZIP upload)update_1.1.0.sql
Fresh install v1.1.0 directly, then activateinstall.sql (already contains everything)
Update from v1.0.0 → v1.2.0 (ZIP upload)update_1.1.0.sql then update_1.2.0.sql in order
Update from v1.1.0 → v1.2.0 (ZIP upload)update_1.2.0.sql only
Deactivate / ReactivateNothing — no SQL runs on toggle

Use qp() in PHP whenever you query your plugin's tables:

$rows = $db->query(qp("SELECT * FROM {items}"))->fetchAll();
// → SELECT * FROM `altcore_plugin_mp_items`
Use INSERT IGNORE and CREATE TABLE IF NOT EXISTS so the SQL file is safe to re-run if something went wrong the first time.

Declaring tables for clean uninstall

Declare your plugin's tables in the manifest under tables. Use the same placeholder names as qp() — without braces or prefix:

"tables": ["messages", "settings"]

When deleting the plugin, a checkbox appears offering to drop these tables. If unchecked, the tables are left intact.

HTTP API endpoints

A plugin can expose one or more HTTP API endpoints that return JSON data. These endpoints are callable on demand — from JavaScript on the front-end, or from any PHP page — and are only active while the plugin is activated.

Declaring endpoints in plugin.json

"api": [
    {"endpoint": "data",  "file": "api/data.php"},
    {"endpoint": "stats", "file": "api/stats.php"}
]
KeyDescription
endpointrequiredURL slug for this endpoint. Lowercase letters, digits, hyphens and underscores only.
filerequiredPath to the PHP handler file, relative to the plugin root.

URL pattern

Every declared endpoint is reachable at:

GET /api/{plugin-id}/{endpoint}

For a plugin with id hello-world and endpoint data:

GET /api/hello-world/data

The endpoint returns 404 JSON automatically when the plugin is deactivated — no extra guard needed in the handler file.

Writing the handler file

The handler is a plain PHP file. All helper functions are available — getDB(), qp(), h(), kcIsLoggedIn(), etc. Content-Type: application/json is set automatically; you can override it if needed.

<?php
// Reached via GET /api/hello-world/data

$db = getDB();

$greeting = $db->query(qp("SELECT value FROM {settings} WHERE `key` = 'greeting'"))->fetchColumn();
$count    = (int)$db->query(qp("SELECT COUNT(*) FROM {messages}"))->fetchColumn();

echo json_encode([
    'greeting'      => $greeting ?: 'Hello!',
    'message_count' => $count,
], JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES | JSON_PRETTY_PRINT);

Consuming from JavaScript

// Output BASE_URL from PHP first so JS knows the site root:
// <script>var SITE_BASE = '<?= BASE_URL ?>';</script>

fetch(SITE_BASE + '/api/hello-world/data')
    .then(function (r) { return r.json(); })
    .then(function (data) {
        console.log(data.greeting, data.message_count);
    });

Consuming from PHP

$raw  = file_get_contents(BASE_URL . '/api/hello-world/data');
$data = json_decode($raw, true);
echo $data['greeting'];

Auth and authorization

The router does not enforce any authentication — API endpoints are public by default. If an endpoint should be restricted, add a session check at the top of the handler file:

<?php
// Require login
if (!kcIsLoggedIn()) {
    http_response_code(401);
    echo json_encode(['error' => 'Unauthorized']);
    exit;
}

Shared helpers (inc/)

A plugin can place PHP functions shared across its pages/, admin/ and api/ files in an inc/ directory. Both the plugin root and any subdirectory (admin/, pages/ …) can have their own inc/:

LocationScope
inc/functions.phpShared across pages, admin and api.
admin/inc/functions.phpAdmin-only helpers — not available to front-end pages or api.

Naming convention

Prefix every function with your plugin's table_prefix value. This prevents name collisions between plugins that could otherwise both define a generic function called getMessages():

table_prefixFunction name style
"hw"hwGetMessages(), hwAddMessage(), hwGetSetting()
"mp"mpGetItems(), mpSaveItem()

Including the file

Use require_once with a path relative to the including file:

Including fromPath to use
pages/mpage.php or admin/msection.phprequire_once __DIR__ . '/../inc/functions.php';
api/endpoint.phprequire_once __DIR__ . '/../../inc/functions.php';
admin/msection.php (admin-only helpers)require_once __DIR__ . '/inc/functions.php';

Example — plugin root inc/functions.php

<?php
// inc/functions.php — shared helpers for the hello-world plugin

function hwGetMessages(): array
{
    global $db;
    return $db->query(qp("SELECT * FROM {messages} ORDER BY id DESC"))->fetchAll();
}

function hwAddMessage(string $text): int
{
    global $db;
    $stmt = $db->prepare(qp("INSERT INTO {messages} (text) VALUES (:t)"));
    $stmt->execute([':t' => $text]);
    return (int)$db->lastInsertId();
}

function hwDeleteMessage(int $id): bool
{
    global $db;
    $stmt = $db->prepare(qp("DELETE FROM {messages} WHERE id = :id"));
    $stmt->execute([':id' => $id]);
    return $stmt->rowCount() > 0;
}

Example — admin/inc/functions.php

<?php
// admin/inc/functions.php — admin-only helpers

function hwCountMessages(): int
{
    global $db;
    return (int)$db->query(qp("SELECT COUNT(*) FROM {messages}"))->fetchColumn();
}
Keep inc/ files to pure functions with no side-effects: no echo, no redirects. Logic that is only needed in admin pages belongs in admin/inc/, not in the shared root inc/.

Packaging a ZIP

Create a ZIP archive of your plugin directory and upload it via Admin → Plugins → Install plugin. Use your OS's built-in archive tool or any command-line ZIP tool — no helper script is required.

# From inside the plugins/ directory — produces a single top-level folder inside the ZIP:
zip -r my-plugin-1.0.0.zip my-plugin/

# Or via git archive — cleanest option, excludes untracked files:
git archive HEAD plugins/my-plugin --prefix=my-plugin/ -o my-plugin-1.0.0.zip
Before zipping, double-check your plugin.json: required fields (id, name, version, description, author), semver version, and that every file referenced in the manifest (pages, admin, api, assets, sql) exists on disk.

ZIP structure

The ZIP must contain a plugin.json at its root, or inside a single top-level directory (the GitHub download format). Both structures are accepted:

Flat (recommended)
plugin.json

  front.php
  detail.php
admin/
  index.php
  settings.php
assets/
  style.css
  app.js

  data.php

The ZIP extractor rejects any entry containing .. or an absolute path. Make sure your ZIP tool does not produce such entries.

Automatically excluded files

The installer silently skips a built-in list of files and directories even if they are present in the ZIP. This acts as a safety net for common dev artefacts left in by mistake:

RuleWhat it skips
.DS_StoremacOS metadata file
Thumbs.dbWindows thumbnail cache
__MACOSX/macOS ZIP artefact directory and all its contents
.git/Git repository data
.svn/Subversion repository data

Rules are defined in PLUGIN_INSTALL_EXCLUDE in includes/plugins.php. Three rule types are supported:

  • Basename — a name with no /, e.g. .DS_Store: skips any file with that name regardless of depth.
  • Directory prefix — ends with /, e.g. __MACOSX/: skips the entire directory tree.
  • Exact path — contains a / but does not end with one, e.g. docs/notes.md: skips that precise path only.

Installing, updating & activating

Installing

  1. Go to Admin → Plugins.
  2. Click Install plugin and upload the ZIP.
  3. The plugin appears in the list with status Inactive.
  4. Click Activate. If the plugin declares a SQL file, the tables are created automatically at this step.
  5. The plugin's front-end pages are now reachable and its admin sections appear in the sidebar.

Updating

Upload a new ZIP via the same Install plugin button. If the plugin is already installed and the ZIP contains a higher version number, the files are replaced automatically and any applicable migration SQL files are executed. The plugin stays in its current state (active or inactive) — no need to deactivate first.

If the uploaded version is equal to or lower than the installed version, the upload is rejected with an error.

SQL migrations

Place migration files in sql/, named update_{version}.sql, containing only the delta for that version. On update the system runs every applicable file in version order. See the Database section for the full explanation and scenario table.

Use CREATE TABLE IF NOT EXISTS and ALTER TABLE ... ADD COLUMN IF NOT EXISTS to keep migrations safe to re-run.

Slug conflicts

The system checks for slug conflicts before extracting the ZIP, at install time, update time, and re-activation. If a plugin declares a page slug or admin section slug that already exists — as a core page file, an admin-created page in the database, a core admin section, or a slug from another active plugin — the operation is rejected with an explicit error listing which slug conflicts and why.

Choose unique slugs, typically prefixed with your plugin id to avoid collisions, e.g. hello-page-lock rather than about.

Multiple pages, admin sections and tables

All three are arrays in the manifest — add as many entries as needed:

"pages":  [ {...}, {...} ],    // each entry = one URL
"admin":  [ {...}, {...} ],    // each entry = one sidebar link
"tables": ["messages", "settings"]  // each entry = one table to offer for drop on delete

A single install.sql can contain multiple CREATE TABLE statements. SQL migrations follow the same rule.

Granting admin access to groups

After activation, go to Admin → Groups, edit the group, and enable the plugin's section slug(s). The links will appear in the sidebar for members of that group.

Deactivating & deleting

  • Deactivate — pages and admin sections are hidden instantly. Plugin files and database tables are left intact.
  • Delete — the plugin must be deactivated first. Deleting removes all plugin files and the DB registration row. If the manifest declares tables, a checkbox lets the admin choose to drop them — otherwise they are left intact.

Security notes

  • Trust — plugins execute arbitrary PHP on the server. Only install plugins from sources you control or fully trust.
  • CSRF — always protect POST actions in admin pages with csrfToken() / csrfValid().
  • Output escaping — always use h() to escape user-supplied data before rendering HTML.
  • SQL injection — always use PDO prepared statements ($db->prepare() + execute()) for any query involving user input.
  • Direct PHP access — PHP files in plugins/ are not directly accessible via URL. Only static assets (CSS, JS, images) in assets/ are served publicly.
  • File uploads — if your plugin handles uploads, validate MIME types, restrict extensions and store files outside the webroot or in a safe subdirectory.

Checking login state

loginRequired(), kcIsLoggedIn() and kcUser() work transparently in both SSO (Keycloak) and local account modes. Never read $_SESSION keys directly — use these helpers instead.

$isLoggedIn is pre-injected on every plugin page — no call needed for public pages that only show different content based on auth state.

// Protected page — one line is all it takes
loginRequired();

// Public page with auth-conditional block — $isLoggedIn already set
if ($isLoggedIn) {
    // logged-in content
} else {
    // anonymous content
}

$userName = $user['username']; // display name
$userMail = $user['email'];    // email address
$userSub  = $user['sub'];      // SSO UUID — empty in local account mode
